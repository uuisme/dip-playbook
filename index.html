文件定位與目的 · 為什麼需要這份框架、怎麼使用
▼

目的

  1. 建立標準化開發流程：讓產品從 需求 → 設計 → 開發 → 上線 有明確流程與文件標準
  2. 提高跨團隊協作效率：明確每個階段 誰負責、何時交付、交付什麼
  3. 提高產品可預測性：提前評估 開發時程、控制 專案風險、管理 需求變更
  4. 降低產品風險：降低需求不清楚就開始開發、理解落差、系統架構不一致

使用方式

  1. 專案啟動時，PO 依本框架建立專案版本，於職能參與矩陣逐列標註「參與 / 不參與」，不參與職能整列刪除
  2. ClickUp 卡片狀態直接對映本文件階段名稱，卡片流轉即流程推進
  3. 各階段通過條件未達成不進入下一階段，由 PO 裁決縮減範疇或延期

※ 開卡方式參閱：DIP 產品開發流程追蹤規範 > 開卡

週期原則與拆期 · 探索期 vs 執行期、拆期機制、週期銜接
▼

探索期與執行期分離

期別長度是否計入季度說明
探索期
Discovery		4 週
探索 W1–W4		不計入前置作業，與上一週期的上線後觀察期並行。每季開工時已有完成立案的項目待做
執行期
Planning → Released		12 週
W1–W12		計入，對齊一季規劃、設計、開發、測試、上線

探索期主要耗用 PO 與需求端的時間，執行期主要耗用 BE / FE / DE 的時間，兩期錯開後資源不互相排擠。

基本週期

執行期 12 週對齊季度，為週期長度，不是交付上限。團隊在週期內評估「可交付的範疇」，而非把範疇塞進週期

拆期機制

拆期判斷點：Ready for Dev（W4 D3–D5）
  • Planning 完成工時估算後，若總工時超出 Development 容量（5 週 × 可投入人力），即啟動拆期
  • 由 PO 與 BE / FE 共同評估本期可交付範疇，未納入項目退回 Backlog 並標註 Phase 2
  • 拆期以完整可交付的使用者價值為切分單位，不切出半套功能（例：可整套延後「報表匯出」，但不可只做建立不做查詢）
  • 拆期決議留紀錄，載明本期範疇、延後項目與理由，作為下期 Backlog 的進場依據

週期銜接

  • Released 後 1~2 週觀察期，與下一週期的探索期並行
  • Phase 2 項目於下一週期直接進入 Planning，不需重跑 Discovery
  • 觀察期回收的指標成效，作為下一週期探索的輸入

8.2 Test Tier 定義（測試優先級 / Release 必要性）

Test Tier 用來定義測試的重要性與執行範圍，決定 Release Gate 條件，不是缺陷嚴重程度。

主要功能 · 高業務影響		主要功能與常用情境，失敗會明顯影響使用，但不一定直接中斷 P0 JourneyRelease 前必須 PASS（依 8.4 測試狀態定義）阻擋發佈
P2 Regression
非核心 · 回歸與邊界		非核心流程、低頻功能、邊界條件、相容性與歷史 Regression不作為單一 Release Gate，但需追蹤修復記錄並追蹤
重點提醒
  • P0 / P1 / P2 是測試優先級，不是 Bug Severity（Severity＝缺陷影響多大；Test Tier＝測試多重要）
  • 所有 Test Fail 都要建立缺陷並追蹤修復
  • 即使是 P2 發現的問題，只要影響重大，Severity 仍可能是 Blocker
  • 即使是 P0 發現的問題，若僅是 UI 顯示問題，Severity 可能是 Minor

8.3 P0 Journey 定義

  • P0 是 Customer Journey，不是 UI Case 或 API Case；任一步失敗，都視為優先修復，並免阻斷 Release
  • P0 Journey 以 End-to-End、含關聯結果驗證為原則（例：建立 → 執行 → 確認外部送達 → 查看報表數據）
  • 各專案於 Planning 測試策略起草時列出本產品的 P0 Journey 清單，依序編號 P0-01、P0-02…

8.4 測試狀態定義

狀態P0（Must Pass）P1（Core Feature）P2（Regression）P3（Non Running）
Stable 正常執行PASSPASSPASSPASS
Flaky 偶發失敗PASSPASSPASSPASS
Broken 系統性失敗FAILFAILFAILFAIL

※ P0 / P1 必須在 Release 前為 PASS（P2 / P3 可在後續處理）

8.5 PROD 回滾判準

以下任一成立即執行回滾，不在 PROD 現場修
  1. 上線驗證清單的主流程項目失敗
  2. 正式資料源接不通或權限設定錯誤
  3. 監控顯示錯誤率或延遲超出上線前設定的門檻
  • 回滾決策者：PO；執行者：BE / FE（DE 資料段包在 BE）
  • 回滾後缺陷退回 STG Fixing 處理，重新走 STG Fixing → Ready for Prod → Released
  • 回滾判準的具體門檻值（錯誤率、延遲）於 Ready for Prod 上線計畫中填入

缺陷分級（Severity，依 Business Impact）

Severity 用來評估缺陷影響程度，不等同於是否迴歸；所有 FAIL 測試皆需建立缺陷並追蹤修復。

等級定義判斷條件（任一符合即適用）對 Release 的影響
Blocker
重大阻斷		 導致 P0 Customer Journey 無法完成，或產生錯誤的 Business Result，或存在不可接受的安全 / 資料完整性 / 權限風險
  • P0 核心流程失敗，無法完成
  • 造成錯誤資料 / 錯誤受眾 / 錯誤發送
  • 資料遺失 / 破壞 / 跨租戶資料外洩
  • 嚴重安全漏洞 / 權限越權
  • 系統回應成功但實際未執行
  • 沒有替代方式完成相同 Business Outcome
 必須修復才能通過 Release Gate
Major
主要缺陷		 功能存在明顯異常，影響部分使用情境或功能，但 P0 Business Outcome 仍可正確完成，且不涉及不可接受的資料或安全風險
  • 核心功能部分不可用或結果不正確
  • 部分使用者 / 條件受影響
  • 可透過其他正式流程或替代方式完成（workaround）
  • 資料呈現異常但不影響實際執行結果
  • 效能明顯退化但仍可完成（超過 SLA）
  • 整合 / API 回應缺少非必要欄位
 應修復（是否阻擋發佈由風險評估決定，PO 裁決）
Minor
次要缺陷		 功能與 Business Outcome 均正確，僅影響使用體驗、顯示或非關鍵操作，不影響資料正確性與安全性
  • UI / 文字 / 排版 / 顏色 / Icon 問題
  • Tooltip / Warning Message 文字不正確
  • 非必要欄位顯示錯誤
  • 輕微效能下降且未超過 SLA
  • 翻譯錯誤 / 文案拼字錯誤
 應追蹤修復，不直接阻擋發佈

Severity 判斷流程

  1. 是否導致 P0 Journey 無法完成？ 是 → Blocker；否 → 下一題
  2. 是否可能造成錯誤的 Business Result？（錯誤資料 / 錯誤受眾 / 安全 / 權限 / 資料遺失） 是 → Blocker；否 → 下一題
  3. Business Result 是否仍可完成，但有部分功能異常？ 是 → Major；否 → 下一題
  4. 功能結果正確，僅影響 UI / UX / 顯示或非關鍵操作？ 是 → Minor
